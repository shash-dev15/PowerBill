# PowerBill College Demonstration Guide

This guide follows the current console implementation in `Main.java` and the project README. It uses an isolated MongoDB database so the normal `powerbill_db` and any validation databases remain untouched. The starter tariff and sample subsidy values below are demonstration values, not official utility rates or policies.

## 1. Start the application safely

Open PowerShell in the project directory. The following command chooses a new database name for this launch, sets the local MongoDB URI, and starts the packaged JAR. It does not drop or modify another database.

```powershell
Set-Location 'C:\Users\Shashank S\OneDrive\Desktop\Console Project\PowerBill'
$env:POWERBILL_MONGODB_URI = 'mongodb://127.0.0.1:27017'
$env:POWERBILL_DATABASE = 'powerbill_presentation_' + (Get-Date -Format 'yyyyMMdd_HHmmss')
& 'C:\Program Files\Java\jdk-21.0.10\bin\java.exe' -jar '.\target\powerbill-1.0.0.jar'
```

If the JAR has not been packaged yet, run `mvn package` from the project directory first. The launch command assumes `target\powerbill-1.0.0.jar` exists. The app connects to MongoDB and creates indexes when it starts. The first run in an empty database seeds five provider names and two explicitly labelled BESCOM demo tariffs.

**Keep the database name for a demonstration session.** The PowerShell environment variables remain set after the application exits, so relaunching from that same window reconnects to the same presentation database. To start fresh, choose a different unique name; do not change the name to `powerbill_db` or a validation database. Do not import the same consumer IDs twice. There is no menu action that drops a database.

## 2. How to navigate

The main menu is:

```text
1 Consumer Management
2 Meter Reading Management
3 Electricity Bill Generation
4 Payment Management
5 Late Payment Management
6 Yearly Consumption Comparison
7 Subsidy Management
8 Consumption Spike Detection
9 Tariff Management
10 Reports and Bill History
11 CSV Import / Export
12 Load Sample Data
13 Database Status
0 Exit
```

Enter the displayed number at `Choice:`. After an operation finishes, the application returns to the main menu; there is no separate back command. For a submenu, enter its displayed number. Use `0` at the main menu to exit cleanly. Invalid choices generally print a validation message and return to the menu. Capture generated consumer IDs, bill IDs, and tariff IDs from the output because later operations ask for those IDs.

Submenus currently implemented:

- **1 Consumers:** Register, List, Search, Update, Delete (deactivate), Billing history.
- **2 Readings:** Enter monthly reading, View consumer history.
- **3 Bills:** Generate new bill, Correct issued bill, View bill.
- **4 Payments:** Record payment, Payment history, Outstanding balances.
- **7 Subsidies:** Create demo scheme, List schemes, Check eligibility.
- **9 Tariffs:** List tariffs, Add tariff version, List configured providers, Add provider, Retire tariff version, Tariff retirement history.
- **10 Reports:** Consumers, Bills, Overdue, Payments, Consumption, Subsidy schemes, Billing summary, Paid/unpaid bills, Applied subsidy history.
- **11 CSV:** Export/import consumers, export/import readings, export/import tariffs, export bills, export consumption history, import consumption history, export a selected report.

## 3. Recommended presentation sequence

The main billing example uses the empty database's seeded BESCOM **DEMO** domestic tariff: first 100 units at ₹2.00, next units through 300 at ₹4.00, and units above 300 at ₹6.00; fixed charge ₹50.00; other charge and adjustment ₹0.00. These rates exist to demonstrate calculation logic only.

### A. Show the database status

At the main menu enter `13`. Expected output starts with `MongoDB connected | database=powerbill_presentation_...` and prints collection counts. A new database has no consumers or bills yet and has seeded provider/tariff records. This is a quick proof that the demonstration is using its isolated database.

### B. Register, find, update, and manage a consumer

Enter `1`, then `1` to register. At the prompts, use:

```text
Name: College Demo Consumer
Address: 10 Demonstration Road
Phone: +919876543210
Category (Domestic/Commercial): Domestic
Provider (e.g. BESCOM): BESCOM
```

The app creates an ID and reports successful registration. Write down that exact ID as `<CONSUMER_ID>`; IDs are generated by the app, so do not assume a fixed value.

To demonstrate search, choose `1`, then `3`, and enter either the ID or `College Demo Consumer`. Expected output shows the consumer's ID, name, address, phone, category, provider, and status. To demonstrate an edit, choose `1`, then `4`, enter the ID, and provide replacement values when prompted. Use `Domestic` and `BESCOM` if you want to keep the subsequent bill example unchanged. `1` then `2` lists consumers. The Delete action is a **soft deactivation**: it asks for the exact confirmation text `DELETE` and retains financial history. Avoid deactivating the demonstration consumer before billing.

### C. Enter a meter reading and explain units

Choose `2`, then `1`. Enter:

```text
Consumer ID: <CONSUMER_ID>
Billing period (YYYY-MM): 2026-11
Previous meter reading: 0
Current meter reading: 250
Meter event (blank, replacement, or rollover): [press Enter]
```

Expected output: `Units consumed: 250`. For a normal meter, consumption is current minus previous. A consumer can have only one reading per billing period; a duplicate is rejected, so choose a new period if repeating this demonstration. `2`, then `2`, followed by the consumer ID, displays that consumer's reading history.

**Optional meter edge cases:** Use a separate consumer and period. For a replacement, choose the `replacement` event and enter the final reading from the old meter when asked; the calculator combines the old meter's final value with the new meter's current value. For rollover, set `POWERBILL_METER_MAX_READING` in PowerShell to the inclusive highest displayed value before launch; its decimal scale defines the register increment. Then enter a lower current reading after the register wraps. For example, a maximum of 100 with readings 95 → 20 yields 26 units, including the step from 100 back to 0. Do not enter a rollover without the setting; it is intentionally rejected. The normal-reading example above is the simplest live demonstration.

### D. Set up and check a demonstration subsidy

Create the scheme before bill generation so it can appear on the bill. Choose `7`, then `1`, and enter:

```text
Scheme name: DEMO College Subsidy
Category or blank for all: DOMESTIC
Eligible up to units: 300
Subsidy amount: 25
Maximum subsidy amount: 30
Effective from YYYY-MM-DD: 2000-01-01
Effective to YYYY-MM-DD: 2099-12-31
```

Expected output: `Demo scheme created.` Schemes must be labelled `DEMO`; the broad dates are only to keep this example in range. Choose `7`, then `3`, and enter `<CONSUMER_ID>`, `2026-11`, and `250`. Expected result: eligible subsidy ₹25.00. The scheme applies to domestic consumers and readings up to 300 units; the amount is capped by the configured maximum. To see the scheme record, choose `7`, then `2`.

### E. Generate and explain a slab bill

Choose `3`, then `1`, and enter `<CONSUMER_ID>` and `2026-11`. A reading for that consumer and period must exist. A second bill for the same consumer and period is blocked. The bill output includes a generated `BILL-...` identifier; record it as `<BILL_ID>`.

Expected calculation for 250 units:

| Item | Calculation | Amount |
|---|---:|---:|
| Slab 1 energy | 100 × ₹2.00 | ₹200.00 |
| Slab 2 energy | 150 × ₹4.00 | ₹600.00 |
| Energy charge | ₹200 + ₹600 | ₹800.00 |
| Fixed charge | Demo tariff | ₹50.00 |
| Other / adjustment | Demo tariff | ₹0.00 |
| Subsidy | Eligible demo scheme | −₹25.00 |
| Payable | ₹800 + ₹50 − ₹25 | **₹825.00** |

The console prints the bill version, consumer, period, provider, units, slab lines, energy/fixed/other/adjustment/subsidy/late fee/payable amounts, due date, and status (`UNPAID`). Choose `3`, then `3`, and enter `<BILL_ID>` to view it again. If your output differs, check that the consumer is domestic, the selected period falls within both tariff and subsidy dates, and no other active demo subsidy was created.

### F. Demonstrate an audited bill correction

Before taking any payment and before applying a late fee, choose `3`, then `2`. Enter:

```text
Issued bill ID: <BILL_ID>
Correction reason: Demonstration correction to meter reading
Type CORRECT to archive and apply this correction: CORRECT
Corrected previous reading: 0
Corrected current reading: 260
```

Expected output is bill version 2 with 260 units and a message that prior bill and reading snapshots are archived. Using the same tariff and scheme, energy becomes ₹840.00 (100×₹2 + 160×₹4), fixed charge ₹50.00, subsidy ₹25.00, and payable **₹865.00**. The correction is audited and recalculates using the original bill's tariff snapshot. A bill with a payment or an applied late fee cannot be corrected; cancellation requires entering anything other than the exact `CORRECT` confirmation. Do not retry bill generation for the same consumer/month to simulate a correction.

### G. Record partial and full payments

Choose `4`, then `1`. Enter `<BILL_ID>` and payment amount `300`; the application automatically assigns a receipt ID and records the payment date and billing period. Expected output includes `Payment Successful!`, a `PAY-######` receipt, and remaining balance **₹565.00**. A payment must be positive and no greater than the current outstanding amount.

Choose `4`, then `1` again. Enter the same bill ID and amount `565`. Expected output: a new receipt ID and remaining balance ₹0.00. Choose `4`, then `2` and filter by the bill ID (or leave blank for all payments) to display each transaction with its receipt ID, billing period, amount, payment date, and status. Choose `4`, then `3` to show payable amount, amount paid, remaining balance, and status for bills.

### H. Late fee: date-dependent demonstration

Late payment management has **no input submenu**: choosing `5` checks unpaid/partially paid bills whose due date is strictly earlier than today. It applies the fee once and prints each bill ID, fee, outstanding amount, and due date. The default due date is 20 days after bill generation, so a newly created bill is not immediately eligible. The normal console does not provide a way to backdate a bill or due date; do not claim an immediate late-fee demonstration on a fresh bill.

For a reliable presentation, prepare a **separate unpaid bill** in the isolated presentation database on the preceding day with `POWERBILL_DUE_DAYS='0'` set before launching. Leave that bill unpaid, exit, then on the next calendar day reopen the same database name and choose `5`. (The test is `today > dueDate`, so same-day is not overdue.) Default demonstration fee settings are 2% of outstanding, minimum ₹10.00, maximum ₹500.00; e.g. an outstanding ₹565.00 yields ₹11.30. The bill total increases by the one-time fee. Payment option `4` also applies the fee when a bill is overdue and is paid. Keep the already-paid primary example bill separate from this overdue example.

### I. Yearly comparison and spike warnings

These features need matching historical records. At the main menu choose `12` once to load clearly tagged simulated data: 30 `SIM-...` consumers and 720 readings/history records over the two most recently completed years. The loader reports that sample data was inserted. If sample consumers already exist in this database, it reports that data already exists and does not duplicate it. Sample generation does not create bills, payments, or subsidy schemes.

For the current calendar year 2026, sample history covers 2024 and 2025. Choose `6` and enter consumer `SIM-002`, month `8`, previous year `2024`, current year `2025`. Expected values are 140 → 230 units, difference 90, increase about 64.29%, trend `INCREASED`. If presenting in a later year, use the two latest completed years shown by the sample generator. `SIM-005` has the deliberate August spike (100 → 360 for those example years).

Choose `8` and press Enter at the default threshold (50). Expected output includes warnings for sample consumer/month pairs whose same-month historical increase exceeds the threshold, followed by `Spike warnings: <count>`. The warning text says to investigate; it is an indicator, not a diagnosis. A comparison with missing records reports insufficient historical records; a zero prior-year value is reported with percentage change `undefined (previous was zero)` rather than dividing by zero.

### J. Tariff and provider management

Choose `9`. Option `1` lists tariff versions and IDs; option `3` lists configured provider IDs. To demonstrate version creation without changing the seeded BESCOM tariff, add a separate provider (`4`) with provider ID `COLLEGE-UTILITY` and region `College demonstration`. Then add a tariff (`2`) for provider `COLLEGE-UTILITY`:

```text
Provider: COLLEGE-UTILITY
Category: Domestic
Tariff name: DEMO Presentation Tariff
Effective from: 2000-01-01
Effective to (YYYY-MM-DD, blank for open-ended): [press Enter]
Fixed charge: 0
Additional charge: 0
Adjustment: 0
Number of slabs: 1
Slab 1 upper units (blank = unlimited): [press Enter]
Rate per unit: 1.50
Source publication/reference (blank means demo): [press Enter]
```

Expected output: `New immutable tariff version added.` A blank source is accepted only because the name contains `DEMO`; it is labelled demonstration-only. Tariff ranges for the same provider/category cannot overlap. Existing bills retain their tariff snapshots.

To demonstrate retirement, choose `9`, then `5`, use the newly listed `COLLEGE-UTILITY` tariff ID, enter a last effective date such as `2099-12-30`, provide reason `College demonstration retirement`, and type exactly `RETIRE`. Expected output confirms retirement and preservation of rate/bill snapshots. Then `9`, `6` shows the retirement history. This is safe in the separate presentation database; do not retire a tariff in a validation or normal database. Adding a new tariff version is how rate changes are represented; existing versions are not edited in place.

### K. Reports and CSV import/export

Choose `10` and enter a report number to display it. Useful presentation choices are `2` Bills, `4` Payments, `5` Consumption, `7` Billing summary, and `9` Applied subsidy history. Empty report results say `No records found.`; billing summary prints bill count, units, billed, payments, and outstanding.

For CSV files, point exports at a temporary folder so generated files do not clutter or replace project files:

```powershell
$csvDir = Join-Path $env:TEMP 'PowerBillCollegeDemo'
New-Item -ItemType Directory -Force -Path $csvDir | Out-Null
```

Choose `11`, select an export, then enter a path such as `Join-Path` output resolved beforehand, e.g. `C:\Users\<you>\AppData\Local\Temp\PowerBillCollegeDemo\consumers.csv`. The app prints success and the row count. Open the exported file with `Get-Content '<full path>'` in PowerShell. A safe quick demonstration is export consumers (option `1`), readings (`3`), tariffs (`5`), bills (`7`), consumption history (`8`), or export report CSV (`10`, followed by a report number such as `7` for billing summary).

Supported imports are consumers (`2`), meter readings (`4`), tariffs (`6`), and historical consumption (`9`). Imports need a correctly headed CSV and validate each row; output gives success and failed row counts and explains invalid rows. Consumer CSV uses `consumerId,name,address,phone,category,provider,status`. Reading import accepts `consumerId,period,previous,current` (or the six-column reading export). History uses `consumerId,period,units,note`. Tariff CSV uses `provider,category,name,effectiveFrom,effectiveTo,fixedCharge,additionalCharge,adjustment,source,slabsJson`; its `slabsJson` must be valid JSON. For a safe import demo, prepare a separate valid CSV with a new consumer ID or a nonduplicate history period. Do not re-import the file you just exported into the same database: consumer IDs and consumer/month records are uniqueness constrained. CSV import does not support bills, payments, providers, correction archives, or subsidy schemes.

## 5. Java architecture for evaluator discussion

The implementation is in the compact `com.powerbill` package:

- `Main` owns console menus, input validation, and application workflows. It coordinates services and persistence; it is also the largest and most tightly coupled class because menu flow and MongoDB operations are combined.
- `BillingEngine` applies progressive slabs and monetary charges using `BigDecimal` and two-decimal rounding.
- `MeterReadingCalculator` contains normal, replacement, and rollover unit calculations.
- `PaymentCalculator` computes balances, late fees, and payment status.
- `ConsumptionAnalytics` handles year comparisons and spike threshold logic.
- `MongoStore` owns the MongoDB client lifecycle, database selection, connectivity, and indexes.
- JUnit tests exercise independent business calculators and Mongo-backed workflows.

The design separates reusable calculation rules from console workflows, but does not use separate model/service/repository/menu packages; MongoDB `Document` records are used at the persistence boundary. This is a reasonable small console-project tradeoff, though `Main` could be split into workflow services if the application grows. Java 21 is used primarily through modern switch expressions and language/API features; the important correctness choice is explicit `BigDecimal` arithmetic for currency and units.

## 6. Likely evaluator questions

**Why use `BigDecimal` instead of `double` for bill amounts?** Binary floating-point cannot represent many decimal fractions exactly. `BigDecimal` with an explicit scale and `HALF_UP` rounding gives predictable currency results.

**How is progressive billing different from charging every unit at the last slab rate?** Each band is charged only for the units inside that band. In the example, 250 units costs 100×₹2 plus 150×₹4, not 250×₹4.

**How do you prevent a duplicate bill?** A consumer/month bill is checked before generation and protected by a unique database index. Corrections use the existing bill ID, increment the version, and archive its prior state; they do not create a second bill.

**Can an issued bill be edited freely?** No. The correction flow requires a reason and exact `CORRECT` confirmation, blocks paid or late-fee bills, recalculates from the original tariff snapshot, and preserves the prior bill and meter reading in correction history.

**What happens when rates change?** A new effective-dated tariff version is added; overlapping ranges for the same provider/category are rejected. Retirement records the before snapshot and reason. Already-generated bills keep their tariff snapshots.

**How is a payment represented?** Each positive payment is a separate record with a unique receipt reference. The app derives outstanding balance and status from the bill total and recorded payments; it rejects amounts above the current balance.

**How is a spike defined?** It is a configurable percentage increase over the same consumer's same month one year earlier. The default threshold is 50%; the output is a warning for investigation, not a conclusion about the cause.

**Are the tariff, subsidy, and late-fee rates official?** No. The seeded tariff and configurable fee/subsidy examples are explicitly demonstrations. The app does not connect to utility customer accounts or verify official rates.

**What does sample data contain?** Thirty labelled sample consumers and 24 monthly meter/history rows each over two completed years. It is for comparisons and spike detection; it does not include bills or payments.

**Why is MongoDB present?** It persists consumers, readings, tariff versions, bills, payments, and history between runs. The calculation classes are Java code and are separate from the database client. A separate database name makes an isolated demonstration possible.

## 7. Known limitations to state accurately

- The console does not provide a way to backdate a bill or its due date. A fresh bill cannot incur a late fee until its due date has passed.
- Sample data creates consumers, readings, and consumption history only; bills/payments must be demonstrated with normal menu workflows.
- CSV imports do not exist for bills, payments, providers, correction history, or subsidies. CSV parsing is line-based and does not support embedded newlines in a field.
- Provider integration is not implemented; configured provider names are local app data only.
- Tariff/subsidy/late-fee values are not official. The program is an educational demonstration, not a production utility billing system.
- The app uses MongoDB without multi-document transactions. It has correction snapshots/recovery, but it is not a fully transactional accounting ledger.
